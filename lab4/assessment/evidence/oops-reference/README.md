# Официальный OOPS REST: методика и результаты

Проверка выполнена self-hosted официальным upstream OOPS! через HTTP REST.
Это отдельный сервис с оригинальными checker-алгоритмами, а не локальные эвристики
optimizer и не ответ публичного production endpoint. Публичный HTTPS REST
`https://oops.linkeddata.es/rest` не ответил из проверенной среды.

Исходники: [oeg-upm/OOPS](https://github.com/oeg-upm/OOPS/tree/11572ea6b31cba29dd3f8a443e24311652f059de),
commit `11572ea6b31cba29dd3f8a443e24311652f059de`, проект 0.3.0-SNAPSHOT.
SHA-256 всех 273 исходных файлов совпали с
[картой происхождения](upstream-source-sha256.json). Алгоритмы pitfalls и
эталонные данные не изменялись.

## Происхождение и изоляция сервиса

Maven 3.9.16 и Tomcat 10.1.61 получены из официальных Apache архивов с проверкой
SHA-512; URLs и суммы приведены в [bootstrap.json](bootstrap.json).
Использован Java 17.0.21 Temurin. WAR имеет SHA-256
`2fab177a7de24180aee24e278ff5d27e9ed3d222b7ac0394080f43c50b7c251f`.
Сохранены журналы сборки и resolved dependencies. Сборка выполнила package с
`-Dmaven.test.skip=true`; полный upstream unit-suite этим не подтверждается.

Maven использовал отдельный m2, пустые user/global settings, MAVEN_SKIP_RC=1
и минимальное окружение без унаследованных токенов. Единственный webapp —
официальный WAR. Manager/admin и системные службы не используются. HTTP привязан
к 127.0.0.1:11438, shutdown — к 127.0.0.1:11439. Процесс ограничен двумя CPU,
heap 768 MiB и nice 10. Jena 5.3.0, OWL API 5.5.1 и Jersey 3.1.10 этого сервиса
изолированы от закреплённого classpath optimizer/lab2.

## Проверка REST

Все 12 REST-случаев на официальных синтетических fixtures совпали с upstream
expected по семантической RDF-структуре выбранной группы: P04, P08, P10/A/B/C,
P11, P13 и четыре варианта P22. Каждый ответ имеет HTTP 200 и Turtle response.
UUID-ресурсы согласованно отображались на blank nodes; предикаты, значения,
datatype, затронутые элементы и связи сохранялись. Отсутствие finding в P10-A/B/C
соответствует upstream expected. [Сводка](fixture-summary.json) и сырые входы,
ответы и сравнения в fixtures/ сохранены.

Отрицательный контроль comparator с намеренно заменённым затронутым элементом
P04 был отвергнут. Проверяется содержимое ответа, а не только HTTP-код.
Исходные expected и ответы не изменялись.

## Результат онтологий

Версии 1.0.0 и 2.0.0 отправлены сервису по одному разу по шести проверкам
P04, P08, P10, P11, P13 и P22. Оба настоящих RDF-ответа сохранены:
[исходная версия](../oops-baseline-reference/result.json),
[итоговая версия](../oops-final-reference/result.json).

| Проверка | 1.0.0 | 2.0.0 |
|---|---|---|
| Локальная метрика Q | 10 | 4 |
| OOPS P13: затронутых свойств | 10 | 4 |
| OOPS P04: затронутых классов | 1 | 1 |
| OOPS: сумма number_affected | 11 | 5 |

Множества P13 совпадают с локальными проверками точно. Единственное дополнительное
замечание P04 — ModelComponent: upstream выделяет корневой класс без участия
в domain/range и соответствующих сложных аксиомах; локальная операционализация
признаёт связью также именованные SubClassOf и DisjointClasses. Остальные четыре
группы замечаний не содержат. Зафиксированная функция F использует локальные Q0=10
и итоговый Q=4; результаты разных операционализаций не смешиваются.
Подробное [сравнение итоговой версии](../oops-final-reference/comparison.json)
содержит точные множества и количества.

## Воспроизведение

Копии scripts и Java helpers находятся здесь. Для новой установки их помещают
в `.local-runtime/oops-reference/` внутри отдельного чистого корня проекта,
предоставляют закреплённый JDK 17 и последовательно вызывают bootstrap.py,
build.py, deploy.py, fixtures.py и audit.py. Нужны оба Java helper:
CompareFixtures.java и SummarizeReport.java. Сохранённые доказательства поставки
не перезаписывают. Scripts выбирают repo/canonical evidence по
DELIVERY_MANIFEST.json в корне.

Для уже квалифицированного экземпляра restart.py проверяет исходники и WAR,
восстанавливает сервис и сохраняет ledger запросов. Он не выполняет setup
поверх существующих результатов. Скрипт final_once.py запускают из runtime-копии
с точными --ontology, --sha256 и новым --output. Он запрещает повторную отправку
по ledger. Прямой запуск runtime scripts из каталога evidence не поддерживается.
Публичный production endpoint этим маршрутом не проверяется.
