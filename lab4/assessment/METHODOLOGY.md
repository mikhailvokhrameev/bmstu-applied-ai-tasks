## Исходник и область подсчёта

Исходник: `lab2/ontology/videocard.owl`. SHA-256:
`d8ac600a45ce642deee38be726ae5d0d81f9e47967a9e1bb07a66b5005ae3661`.
Перед любым расчётом/поиском проверить SHA; несовпадение прекращает процедуру. Существующий файл не изменялся.

Считается множество явных аксиом корневой онтологии (без imports closure и без вывода reasoner), не RDF-тройки и не строки XML. Повтор идентичной OWL-аксиомы не увеличивает счётчик. Пользовательские сущности имеют IRI `https://example.org/ontologies/videocard#…`; встроенные сущности, в том числе owl:Thing и owl:Nothing, не входят в C. A — все аксиомы корневого пользовательского документа, включая объявления и аннотации; Al — только логические аксиомы OWL API. Аннотации самой онтологии и ontology/version IRI не являются аксиомами и в A не входят. Документы с импортами/посторонними пользовательскими пространствами не входят в данный эталон: при их появлении требуется отдельное решение об области подсчёта до поиска.

C, Po, Pd — различные классы, объектные свойства и свойства данных из сигнатуры в пользовательском пространстве; индивидуальные сущности для этих трёх счётчиков не учитываются. H — число явных SubClassOf, у которых обе стороны — именованные пользовательские классы; ограничения и anonymous superclass не учитываются. E — число различных именованных пользовательских классов, участвующих непосредственно как операнды EquivalentClasses (не число аксиом и не число вложенных классов выражения). N — число именованных пользовательских индивидов. Неподдерживаемое разделение сущностей при punning не используется в исходнике и контрольных данных.

| C | H | Po | Pd | E | Al | A | N | SubClassOf всего | EquivalentClasses аксиом | DisjointClasses |
|---|---|---|---|---|---|---|---|---|---|---|
|15|5|10|7|2|253|472|41|16|2|3|

M1=H/C=1/3; M2=Po/(H+Po)=2/3; M3=Pd/C=7/15; M4=E/C=2/15; M5=Al/A=253/472. Использовать эти точные дроби, а не округлённую таблицу ТЗ. M6=Q. Для пустого знаменателя метрика не определена: расчёт должен завершаться диагностикой, кандидат невалиден; молча подставлять 0 запрещено. Нулевой числитель при ненулевом знаменателе даёт 0.

## Локальные проверки и единицы нарушений

Это детерминированная локальная операционализация шести категорий OOPS!, а не копия недокументированной реализации веб-сервиса. Область проверок — только C, Po, Pd; индивиды, аннотационные свойства и внешние словари исключены. Каждое нарушение хранится с кодом и ключом; Q — мощность множества `(код, ключ)`. Между проверками дедупликации нет. Внутри проверки одинаковый ключ учитывается один раз.

| Код | Условие и единица | Минимальное нарушение | Отсутствие нарушения |
|---|---|---|---|
|P04|Сущность не участвует ни в одной логической аксиоме, сигнатура которой содержит хотя бы две различные сущности из C/Po/Pd. Единица — IRI сущности. Объявления и аннотации не связывают.|`Declaration(Class(:A))` без логики → A|`SubClassOf(:A :B)` → A и B связаны|
|P08|Нет непустого literal rdfs:label@ru или rdfs:comment@ru. Единица — `(IRI, label/comment)`; если отсутствуют оба, два нарушения. Только язык ru, регистр языкового тега несущественен.|A имеет только label@ru → один недостающий comment|A имеет label@ru и comment@ru → 0|
|P10|Неупорядоченная пара различных именованных классов имеет общий непосредственно записанный именованный superclass, но нет явного DisjointClasses с обоими операндами. Единица — отсортированная пара IRI, независимо от числа общих родителей. Не утверждает, что любые siblings обязаны быть несовместимы: эвристическое предупреждение для экспертной проверки.|`SubClassOf(:A :B)`, `SubClassOf(:C :B)` → (A,C)|Дополнительно `DisjointClasses(:A :C)` → 0|
|P11|Нет явного domain либо range для объектного свойства/свойства данных. Единица — `(IRI, domain/range)`; оба отсутствуют → 2. Anonymous union, restriction и datatype допустимы. Унаследованные domain/range не засчитываются.|ObjectProperty p с domain, без range → (p,range)|Явные `ObjectPropertyDomain(:p :A)` и `ObjectPropertyRange(:p :B)` → 0|
|P13|Нет явного InverseObjectProperties с данным именованным свойством и нет SymmetricObjectProperty для него. Единица — IRI объектного свойства; data properties исключены.|p без inverse/symmetric → p|`InverseObjectProperties(:p :q)` → для p и q 0; symmetric p → 0|
|P22|Локальное имя класса не соответствует `[A-Z][A-Za-z0-9]*`, либо имя свойства не соответствует `[a-z][A-Za-z0-9]*`. Полное совпадение ASCII regex, допускаются аббревиатуры GPU, суффиксы цифр. Единица — тип сущности и IRI.|Класс `bad_class` → 1|Класс `GPUModel`, свойство `usesGPU` → 0|

В примерах рассматривается только указанная проверка; сопутствующие предупреждения остальных категорий не исключаются. P04 допускает связанную изолированную компоненту и не требует единого графа; P10 не ищет все несвязанные пары и не использует вывод; P08 строже общих рекомендаций по аннотациям, P22 фиксирует локальный стиль вместо статистической эвристики. Это ожидаемые причины расхождения с OOPS!. P13 — рекомендация оформления, а не логический дефект, добавление обратного свойства требует предметного обоснования.

В исходнике P04=P08=P10=P11=P22=0; P13=10, по одному на каждое из десяти объектных свойств (полный перечень в `evidence/baseline-audit.txt`). Таким образом Q0=10 по этой версии локальной методики. Это не результат проверки веб-сервисом. Веб-OOPS! не запускался; исходник и финал ещё должны быть проверены однократно, с сохранением ответа и сравнением ключей/областей. Попытка прочитать каталог https://oops.linkeddata.es/catalogue.jsp завершилась timeout; названия категорий сверены с авторским материалом https://linkedbuildingdata.net/ldac2022/summerschool/files/presentations/MPovedaVillalon_ontologies.pdf через поисковую выдачу. Полное воспроизведение поведения OOPS! не заявляется.

## F и контрольные данные

Для i=1…5: ri=min(Mi/Mi0,2); r6=min(11/(Q+1),2). F=0.15r1+0.15r2+0.10r3+0.15r4+0.15r5+0.30r6. Для исходника все ri=1, F0=1. В `fixtures/expected.json` и CSV — точные дроби и десятичный F для трёх малых онтологий Functional Syntax. Это независимые модульные эталоны формул, не кандидаты для добавления к ядру. При запуске полного валидатора они не сохраняют ядро и получают F=0; их табличный F — значение формулы ДО проверки валидности. Требование ri≥0.85 применяется к кандидатам, не к этим модульным примерам.

Ручной подсчёт:

* 01-balanced: 2 класса + p + value = 4 объявления, 8 аннотаций, 6 явно перечисленных логических аксиом → A=18, Al=6; H=1, E=1, Q=1 (нет обратного p). M=(1/2,1/2,1/2,1/2,1/3,1). До ограничения r4=15/4, r6=11/2; оба ограничиваются 2.
* 02-zero: A и p = 2 объявления + 4 аннотации + domain/range = 8; Al=2; H=E=Pd=0. M=(0,1,0,0,1/4,1). Все знаменатели ненулевые; проверяет нулевые числители. r6 ограничивается 2.
* 03-pitfalls: 4 класса + p + value = 6 объявлений; 11 аннотаций (нет comment у bad_class); 6 логических аксиом → A=23. H=2, E=1. По одному нарушению каждого кода → Q=6. M=(1/2,1/3,1/4,1/4,6/23,6).

Счётчики заданы вручную независимо от ReferenceAudit; производные дроби вычислены стандартным Fraction. Числа из OWL API сверены отдельно, результат в `evidence/fixture-audit.txt`. Парсер распознаёт builtin owl:Thing в сигнатуре исходника, поэтому использовать `getClassesInSignature().size()` без фильтрации было бы ошибкой (16 вместо 15).

20 пар в `concept_pairs.csv`: 10 положительных и 10 отрицательных, статус каждой `pending_system_analyst`. Метки — предложенный эталон, не согласованный аналитиком. В частности, «производитель видеокарты» и «производитель GPU» — разные роли даже при совпадении организации. Оценка косинусных расстояний и подтверждение порога 0.90 ещё не выполнены; до этапа 3 нужны утверждённая разметка и embedding-модель.

## Существующий harness lab2

`bash lab2/tests/run_tests.sh` проверяет/загружает закреплённые JAR по SHA-1, компилирует `src/*.java` и запускает Main. Эквивалентные команды из корня:

```sh
bash lab2/tests/harness/fetch_libs.sh
mkdir -p lab2/tests/harness/out
javac -encoding UTF-8 -cp 'lab2/tests/harness/lib/*' -d lab2/tests/harness/out lab2/tests/harness/src/*.java
java -Dfile.encoding=UTF-8 -Dslf4j.internal.verbosity=ERROR -cp 'lab2/tests/harness/out:lab2/tests/harness/lib/*' Main lab2
```

Закреплены OWL API 4.5.29 и HermiT 1.4.3.456. Полный перечень транзитивных зависимостей — `fetch_libs.sh`, Maven не нужен. Журнал реально выполненного запуска: `evidence/lab2-run-tests.log`, 11/11 групп PASS. Старые результаты не использованы как замена запуску.

T05DlQueries.java сравнивает множества с независимым `lab2/tests/expected.json`: Q1 изготовитель (P1/P2); Q2 GPU (G1–G5); Q3 ≥8 GiB; Q4 тип памяти (GDDR5/6/6X); Q5 активное охлаждение; Q6 выходы (DVI/DisplayPort/HDMI/VGA); Q7 PCIe (3/4/5); Q8 пересечение Q3 и Q5. Проверяются все аргументы, не только representative; для Q3/Q5/Q8 сравниваются определяемые классы и raw Manchester expressions, принадлежность должна выводиться. Q3={U02,U03,U04,U06,U07}; Q5={U02,U03,U04,U05,U07}; Q8={U02,U03,U04,U07}. Остальные полные ожидаемые множества остаются в expected.json.

NegativeCopyTest сравнивает наборы аксиом финала и дефектной копии, не допускает посторонних изменений. T06 добавляет PassiveCooling для Cooling_Active_2fan → inconsistent. T07 добавляет U01 usesGPU GPU_G2 при исходном GPU_G1 и DifferentIndividuals → inconsistent. T08 заменяет 4 positiveInteger на −8 integer у Mem_4GiB_GDDR5 → inconsistent по range; после удаления range из временного варианта consistent, что исключает ложное объяснение функциональностью. T09 удаляет U05 hasMemory Mem_6GiB_GDDR6 → consistent по открытому миру, но completeness card даёт ровно одну ошибку `(U05,hasMemory,0,1)`. Возвращённый исходник проверяется отдельно.
